# Разработка и тесты

[English](../development.md) · **Русский**

Как развернуть проект, какие есть наборы тестов и что нужно каждому из них, и как снимаются скриншоты в настоящем приложении Paseo.

## Установка

```bash
git clone https://github.com/DrStannum/paseo-plugin-beads.git
cd paseo-plugin-beads
npm install                 # только определения типов и инструменты для тестов
paseo plugin install .      # демон собирает и загружает плагин из этого каталога
```

У плагина **нет рантайм-зависимостей**: всё, что он импортирует во время работы,
предоставляет хост Paseo (`react`, `react-native`, `@tanstack/react-query`,
`zod`, `@getpaseo/plugin`) либо это модуль `node:*` на стороне сервера.
`devDependencies` нужны для проверки типов и тестов. Node 22.18 и новее запускает
тесты на TypeScript напрямую, без шага сборки.

После изменения `paseo plugin reload beads` заставляет демон пересобрать плагин, и
открытые панели подхватывают новую версию. Перезапускать демон не нужно.

Клиентский код работает на Hermes под iOS и Android, поэтому не выходит за пределы
того, что Hermes поддерживает: никаких `class`, `Array.prototype.toSorted`,
lookbehind и флага `v` в регулярных выражениях, `Intl.Segmenter`.

## Наборы тестов

```bash
npm run typecheck   # tsc --noEmit
npm run smoke       # RPC-обработчики против записывающей заглушки bd, за секунды
npm run write       # путь записи против настоящего bd во временном проекте, около минуты
npm test            # typecheck + все tests/*.test.ts (smoke, write и чистая логика)
npm run preview     # все скриншоты в настоящем Paseo web плюс сценарные проверки, около 20 минут
npm run bench       # тайминги на большом синтетическом проекте, около 3 минут; не входит в npm test
npm run bench:open  # тот же проект, открытый в настоящем Paseo web, около 7 минут; не входит в npm test
```

Что нужно каждому:

| Скрипт | Что нужно |
|---|---|
| `npm run typecheck`, тесты логики | ничего, кроме `npm install` |
| `npm run smoke` | ничего: `bd` — заглушка, которую тест кладёт в `PATH` |
| `npm run write`, `npm test` | настоящий `bd` в `PATH`; тест сам создаёт и удаляет свой проект |
| `npm run preview`, `npm run shot*` | запущенный локальный демон Paseo с загруженным плагином, `bd` и Playwright с Chromium |
| `npm run bench` | настоящий `bd` |
| `npm run bench:open` | то же, что `npm run preview`; ещё он перезагружает плагин (`paseo plugin reload beads`) |

**`tests/support/harness.ts`** вызывает RPC-обработчики плагина так же, как это
делает демон, но без него: ввод разбирается контрактом, обработчик работает с
фейковым контекстом, где поиск рабочего пространства отвечает из таблицы, а вывод тоже
разбирается контрактом, так что ответ, не подходящий под свою схему, роняет тест
точно так же, как уронил бы RPC.

**`tests/smoke.test.ts` и `tests/smoke-write.test.ts`** гоняют обработчики против
заглушки `bd`, записывающей argv, и после разбирают журнал, так что инварианты
проверяются исполнением кода, а не чтением исходников: каждое чтение несёт
`--readonly`; запись приходит только из RPC записи, только с подкомандой из
закрытого набора, никогда с `--readonly` и всегда с `--dolt-auto-commit off`;
`delete`, `init` и `sync` отклоняются ещё до запуска `bd`; неизвестное рабочее
пространство отвечает `unknown_workspace` из каждого RPC, а каталог без `.beads` — `no_beads`.
Кеш снимков нарочно проводится через сбой: параллельные запросы после сдвига
ревизии запускают один `bd list`; `have` отвечает `unchanged` без строк; с `deltas`
изменённая, удалённая или добавленная задача приходит дельтой, которая поверх
имеющихся строк даёт ровно полный ответ — и когда ревизия сдвигается во время
чтения, — а неизвестная `have`, большой разрыв или ответ `stale` получают полный
набор (чистый дифф и кольцо ревизий — юнит-тесты в `tests/history.test.ts`, рестарт —
в `tests/snapshot-disk.test.ts`); падающий
`bd list` отдаёт последний удачный снимок с пометкой `stale`; загрузка дольше
бюджета обработчика отвечает `busy` и оседает в кеше; строка журнала называет
причину без текста задач.

**`tests/write.test.ts`** делает то же против настоящего `bd`: создаёт одноразовый
проект, прогоняет правки полей, закрытие и переоткрытие, теги, комментарии с
автором и без, смену родителя, очередь экспорта, подсунутый сбой экспорта и его
починку и Sync в обе стороны (устаревший файл не затирает более свежую работу), а
потом удаляет проект.

**`tests/disk.test.ts`** проверяет дисковое хранилище снапшотов
(`server/beads/disk.ts`) во временном каталоге (`CBD_CACHE_DIR`), никогда в
настоящем `~/.paseo`: каталог 0700, файлы 0600 даже при пустом umask; сохранённый
снапшот читается обратно с тем же графом; битый, обрезанный, чужой файл или файл
другого формата читается как «ничего» и удаляется; оборванная запись оставляет
только временный файл, которого не видит чтение и который убирает уборка; лимиты
размера, уборка по простою и по давности использования; два процесса, сохраняющие
одновременно, оставляют один целый файл.

**`tests/snapshot-disk.test.ts`** проверяет это хранилище в связке с чтением, против
заглушки; рестарт имитируется сбросом памяти при сохранённых файлах: удачная
загрузка сохраняется после ответа, неудачная — никогда; при той же ревизии дерево,
карточка и поиск отвечают из файла без запуска `bd`; при сдвинувшейся ревизии
старая копия отвечает сразу, а за ней идёт один `bd list`, и следующее дерево с
`have` получает свежие строки (или старые с пометкой stale, если загрузка упала);
нет файла или он битый — обычная холодная загрузка; правка после рестарта никогда
не планируется против старой копии; первый опрос ревизии прогревает проект уже
после ответа; архивирование рабочего пространства удаляет его файл, если тот же `.beads`
не открыт другим рабочим пространством; `contribute()` возвращается сразу, а уборка идёт после
него — или не идёт вовсе, если плагин остановили раньше.

Остальное — чистая логика: дерево, фильтры и поиск (`tree`, `filters`), колонки
доски и арифметика перетаскивания (`board`), списки «моей работы», счётчики и
поиск боковой панели (`explorer`), дифф формы редактирования и схема
настроек (`form`), агрегации и сцены графиков (`charts`, `chart-scene`,
`charts-view`), отрисовщик Markdown с враждебными входными данными (`markdown`),
таблицы строк обоих языков (`strings`) и документация (`docs`: каждая страница
есть на обоих языках, каждая относительная ссылка и картинка находится, и каждый
скриншот показан в галерее).

## Стенд для скриншотов

`npm run preview` (`tests/preview.mjs`) запускает четыре скрипта один за другим,
каждый в своём процессе: `shot.mjs` (дерево, карточка, фильтры, раскладка),
`shot-board.mjs`, `shot-charts.mjs` и `shot-writes.mjs`. Каждый можно запустить
отдельно и сузить до кадров, в имени которых есть заданное слово:

```bash
npm run shot -- --only stale
npm run shot:board
npm run shot:charts -- --only flow
npm run shot:writes -- --e2e     # только сквозной проход через UI
```

Как это работает (`tests/lib/paseo-web.mjs`):

- **Настоящее приложение.** Демон на `127.0.0.1:6767` не раздаёт свой веб-интерфейс,
  но бандл лежит на диске; Playwright отвечает на запросы страницы из этого бандла
  и пропускает `/api/*` к демону, так что у страницы собственный origin демона, и
  она подключается как любой клиент.
- **Рабочее пространство с фикстурой — только на время прогона.** `tests/fixture/` собирает
  синтетический beads-проект (в режиме `bd` или `jsonl`, при желании с историей
  команды или несколькими тысячами задач) по фиксированному пути, регистрирует его
  как проект Paseo и фоновое рабочее пространство и после удаляет и то и другое — в том числе
  по Ctrl+C. Больше ничего в демоне не трогается, а скриншоты обрезаются по панели,
  так что боковая панель никогда не попадает в PNG.
- **Детерминированные кадры.** Фиксированные отметки времени в фикстуре, часы
  страницы остановлены на собственном «сейчас» фикстуры, анимации выключены.
  Настройки плагина (интервал опроса в каждой шапке, имя на странице настроек) на
  время прогона закреплены на значениях по умолчанию, а прежний файл настроек при
  выходе возвращается в точности; прогон, убитый наглухо, откатывает следующий.
- **Сценарные проверки.** Скрипт доски перетаскивает карточку мышью и проверяет
  через `bd show`, что статус записан; скрипт записи через UI редактирует, создаёт,
  комментирует, подписывает комментарий именем, заданным на странице настроек, и
  синхронизирует, а каждый результат проверяет через `bd`. Кадры боковой панели
  рисуются с именем читателя, заданным на время прогона (потом — снова значение
  по умолчанию), считают RPC страницы — открытие боковой панели рядом с
  загруженной вкладкой не шлёт `beads.tree` — и проверяют, что выбранная строка
  открывает свою карточку во вкладке.

Прогон заканчивается проверкой галереи: каждый `tests/preview-*.png` нарисован этим
прогоном (иначе это сирота, и её нужно удалить), каждый нарисованный PNG перечислен
в заголовке «Frames:» своего скрипта, и каждая строка там что-то рисует. Новый кадр
начинается со строки в «Frames:» и строки в [Скриншотах](screenshots.md).

**Никогда на настоящем проекте.** Скриншоты и замеры делаются только на
синтетической фикстуре: в тексте задач бывают секреты. Нужен объём? У фикстуры для
этого есть опции (`many`, `rich`, `people`, а `mine` — для списка «моей работы» побольше); не создавайте задачи в кадре через
`bd create` — он выдаёт случайные id и текущие даты.

**Если меняете UI, перезапустите затронутые кадры, посмотрите на них и закоммитьте
PNG**: это одновременно иллюстрации документации и регрессионные фикстуры.

## Бенчмарки

`npm run bench` (`tests/bench-large.ts`) собирает проект из 4000 задач по нескольку
килобайт текста в каждой, замеряет `bd list` и `bd comments` поодиночке и по четыре
сразу, потом обработчики внутри процесса: холодное дерево, неизменившееся дерево,
карточку, на сколько одна запись дискового снапшота занимает плагин, дерево после
рестарта из дискового кеша (с той же ревизией и со сдвинутой правкой мимо плагина:
сразу дисковая копия, потом свежие строки дельтой), три холодных дерева сразу, опрос
ревизии, а также размер ответа «не изменилось» и дельты после одной правки в байтах.
Утверждает он только то, что каждое чтение отвечает в пределах 30 секунд демона, а
дерево с диска — в пределах одной; остальное — для чтения. Из этих
чисел и взялись 15-секундный таймаут чтения, 60-секундный лимит `bd list` и
25-секундный бюджет обработчика.

`npm run bench:open` (`tests/bench-open.mjs`) регистрирует такой же проект в Paseo и
замеряет то, чего пользователь ждёт в веб-приложении: от клика до первой строки
дерева при холодном открытии панели (сразу после перезагрузки плагина, в чистом
браузере), при тёплом (вкладку закрыли и открыли снова), второй вкладкой из меню
«+», после перехода на другую вкладку и обратно, от переключателя вида до
нарисованных графиков и после перезагрузки плагина при открытой вкладке; а ещё —
сколько после правки одной задачи через `bd` мимо панели и возврата страницы на
передний план ждать ответа дерева (дельты). Холодное открытие после перезагрузки
отвечается из дискового снапшота сервера; холодное без него (`a0`, полный `bd list`)
прогоняется один раз в начале, если снапшота у проекта ещё нет. Время меряется в
странице наблюдателем, взведённым до клика: от его pointerdown до первого кадра с
элементом, так что занятый главный поток не задерживает сам замер. Для каждого случая
он ещё считает запросы `beads.*`, время самого долгого запроса дерева туда-обратно и
байты ответов (по кадрам WebSocket страницы), отличает полный ответ дерева от дельты
и «не изменилось» и перечисляет размеры ответов. Каждый из трёх прогонов (`--runs`)
начинается с перезагрузки плагина; в таблице — медианы. `--n`, `--keep`
и `--dir` работают как в `npm run bench`, и фикстуру, оставленную одним, можно
отдать другому.
